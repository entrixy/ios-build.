# Порядок автономной работы

Решение пользователя 19.11.2026: результат и экономный расход токенов важнее
скорости. Продолжать полный перенос Android, не останавливаться после каждой
правки или теста. Отчёты не требуют нового разрешения на уже порученную работу.

## Источники и память

- Сначала прочитать указатель в private/WORK_CONTEXT.md и краткую текущую сводку.
  [CURRENT_STATUS.md](CURRENT_STATUS.md) содержит проверенный baseline, активный
  пакет, остаток и точные ссылки на доказательства. Обновлять сводку после
  результата, не накапливать в ней всю хронологию.
- [ANDROID_STRUCTURE.md](ANDROID_STRUCTURE.md) и
  [ANDROID_IOS_PARITY.md](ANDROID_IOS_PARITY.md) задают состав и порядок функций.
  Перед изменением конкретной функции читать соответствующий Android source.
  Сохранять утверждённые общие компоненты и расположение действий.
- Для каждого незакрытого пункта записывать: Android-путь → iOS-путь → пробел →
  критерий приёмки → доказательство. Проверять конкретные файлы и диапазоны;
  исторические отчёты читать только для нужного решения или сбоя.

## Один законченный пакет

1. Выбрать связанный набор оставшихся задач и заранее определить результат.
   Реализовать все его зависимые пути: UI, состояние, сохранение, wire contract,
   восстановление после ошибки. Не добавлять произвольных функций.
2. Во время реализации выполнять дешёвые проверки по затронутой области.
   Тесты добавлять для существенных контрактов/рисков. Syntax parse не выдавать
   за SDK typecheck. Не повторять неизменённое ядро ради текста или документации.
3. Зафиксировать согласованный исходный код, затем один Apple-прогон:
   сборка продуктов один раз, Release/privacy/isolation, hosted+UI в одном
   проходе симулятора со снимками в точках тех же сценариев, iPhone archive.
   Пока полезный прогон идёт, не отменять его очередным микрокоммитом.
4. Ждать через инструменты, не рассуждать повторно над неизменным статусом.
   Опрос автоматический и редкий; в модель возвращать смену этапа/итог.
   Полные логи хранить локально, читать сводку и контекст конкретной ошибки.
5. Все найденные дефекты разобрать вместе: продукт, стенд или инфраструктура.
   Исправить пакет причин, затем повторить нужные проверки. После двух полных
   прогонов с одинаковым неустранённым симптомом перейти к узкому воспроизведению
   и сбору доказательств; не повторять полный набор с очередной догадкой.
   Инфраструктуру повторять автоматически один раз только при явном transient
   сбое. Не ослаблять утверждения ради зелёного результата.
6. Проверить оригинальные кадры визуально. Публиковать полный успешный набор
   точно того же source, с хешами; проверить доступность и работу галереи.
   Сохранять старый набор приватно. Не ретушировать и не рисовать интерфейс.
7. Обновить краткую сводку, критерии и коммиты. Доложить завершённый результат
   и перейти к следующему разрешённому пакету без вопроса «продолжать?».

## Границы отчёта и остановки

Различать: source реализован; автоматические проверки пройдены; кадры
просмотрены; Android/iOS совместимость и оборудование приняты; выпуск готов.
Не оценивать весь App Store результат по количеству тестов или субъективному %.

Короткие сообщения во время работы — о новых фактах. Полный отчёт — после
законченного пакета. Если нужен доступ, идентификатор или действие пользователя,
собрать один конкретный запрос с уже подготовленным результатом и продолжать
остальную независимую работу. Время ожидания не является ответом/разрешением.
Не придумывать credentials, hardware результаты или платформенные возможности.
Намеренные существенные отступления от Android описывать до их реализации.

Исходный код не публиковать в новые места и не менять видимость репозиториев.
Использовать существующий разрешённый CI branch, сохранять секреты/артефакты
вне Git и беречь посторонние изменения живого PHP-сайта.
